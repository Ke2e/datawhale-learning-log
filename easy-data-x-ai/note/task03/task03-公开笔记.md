## P2：RAG 的 R 是检索，不是向量

我对 RAG 的第一印象就是「向量数据库 + 相似度搜索 + 大模型回答」。P2 开头直接把这个印象拆了：RAG 的重点是 Retrieval，而检索不只有向量检索，全文、标量过滤、图谱跳转、API 调用都算。**只要在生成前先去外部取信息，广义上都属于 RAG。**

这个纠正对我有实际意义。Task02 的 P1 里我写过一句话：数据获取已经比设计 RAG 更重要、更难。当时那只是直觉；P2 把它变成了可以执行的东西——你要负责的不是「接一个向量库」，而是「找什么、去哪里找、何时找、怎么合并、能给谁看」。

课程用了一个很具体的例子：用户问 seekdb 1.2.0 的兼容性，纯向量检索可能返回 1.0.0 的文档，因为在向量空间里两句话「语义非常相近」。企业知识库里全是版本号、错误码、产品型号，这些内容向量表示都差不多，但必须字面命中。

所以我的理解是：**混合检索不是高级玩法，而是问题本身就有多个维度决定的。** 语义、精确、范围、实时，各是一路，单靠向量只能覆盖第一路。

## I2：纯向量不够，机制上说得通

I2 给的是 P2 那句话的技术解释，这也是我把两篇放在一起写的原因。

Embedding 把内容变成可比较的向量，但向量不是事实本身。它适合做候选召回，不适合当唯一证据——不可还原原文，也可能把「意思相近」当成「事实相同」。I2 还强调向量旁边要记录 embedding_model、embedding_version、维度、内容哈希，否则模型升级后只重算新数据，检索就会悄悄失效。这一点我原来完全没意识到，属于「不出错就想不到」的那类设计。

距离和索引部分，我的概括是：余弦、点积、欧氏距离是在选「怎么算接近」；HNSW、IVF、量化是在选「用多少精度换速度或空间」。没有哪个索引更好，只有和查询负载、召回目标是否匹配。

混合检索那段给了我一个具体答案：不同召回器的分数不能直接相加，所以 RRF 用名次融合，而不是拿向量距离和 BM25 分数硬比。再往后是两阶段检索——先低成本召回 50～200 条，再用重排模型精排，最后 5～20 条进上下文。候选不是越多越好，它会同时抬高召回率、成本和上下文噪声。

这条链路让我第一次看清 P2 说的「检索路径设计」到底在调什么：不是调一个参数，而是召回、过滤、融合、重排、组装每一环都有取舍。

## 传统 RAG 和 Agentic RAG：差别在有没有环

P2 对两者的区分我很认同：传统 RAG 不一定简单，它可以有改写、路由、多路召回、重排，但整体还是预先写死的无环流程；Agentic RAG 的变化不是节点更多，而是流程里出现了闭环，系统能在运行时决定要不要再搜、换一路、补搜。

这一点我在 d1_5 里有真实观察。跑 `d1_5_tool_use_seekdb.py` 时，模型第一次检索之后没有直接回答，而是**自己改写了 query，又调了一次检索工具**，拿到第二轮结果才组织答案。当时我只是觉得「它会自己想办法」，读完 P2 才反应过来：这就是「要不要再搜、怎么改写」从写死的流程交给了模型判断。我原本以为多轮检索是框架控制的，实际是模型在每一轮输出里自己决定的。

I2 说的召回、过滤、融合、重排、组装，其实描述的是**每一轮内部**的动作；Agentic 只是在外面又加了一层「这一轮够不够」的判断。两者不是替代关系，而是一个套一个。

读 `d1_6_agent.py` 时我还注意到第 49 行用 `threading.Lock` 把 seekdb 查询包了起来。它和「有环」是两件事，但提醒我同一件事：循环不是免费的，多工具并行会被单连接压回串行，延迟和成本都要算进去。

## 三层归因：大多数问题在数据层

P2 最有用的部分是三层归因：数据层（检索不到，或检索到了错误内容）、模型层（检索对了但模型添油加醋）、业务层（答案没错但不合规、不适合场景）。课程给出的实践经验是，认真归因时 60% 到 80% 的「AI 答错」落在数据层，真正的模型幻觉通常只有 10% 到 20%。

配套的决策树把这件事变成了四个可执行的问题：知识库里有没有正确答案 → 有的话 AI 检索到了吗 → 检索到了回答和证据一致吗 → 一致但适合业务场景吗。

我想补一个自己的推论：**循环能救检索路径，救不了数据缺失。** d1_5 里模型主动改写 query，说明它在努力补第一轮的不足；但如果知识库里压根没有那条内容，再搜几轮也搜不出来。这刚好解释了三层归因里为什么「内容覆盖」排在检索策略前面——后者是优化，前者是前提。

## 选型：P2 和 I2 落到了同一个结论

I2 的选型部分列了两条路线：专用向量数据库，或者在现有数据库里扩展向量能力。判断维度是数据规模、查询负载、写入方式、是否强依赖 SQL 和 Join、一致性、多租户权限、部署形态、团队运维成本。

这和我 Task02 读 I1 时的理解接上了：AI 原生数据库把关系、向量、全文和检索放进一个引擎，主要受益者是数据规模中等、不想维护多套系统的小团队。I2 里「业务数据与向量、权限过滤紧密耦合时优先统一数据库」几乎是同一句话的技术版本。

我也记住了 I2 最后那句提醒：**先明确工作负载和验收指标，不要先选产品再为产品找场景。** 这和我平时容易犯的毛病正好相反——看到一个新数据库就想找机会用上。

## 本次 Task 的感受

这两篇放在一起读，比我单独读任何一篇都值。P2 负责「判断问题在哪一层」，I2 负责「这一层的技术选项长什么样」，中间的连接点是「检索」这个词。

之前我对 RAG 的理解停留在「向量库 + 大模型」，现在至少知道：向量只是 R 的一路，循环只是让检索可以重来，而归因才是决定把力气花在哪的第一步。
