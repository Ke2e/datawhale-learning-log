Task02 里我写下过一个判断：Agent 的天花板在数据，不在模型。这次的两篇正好把这句话往两个方向各推了一步——D2 回答"Tool Use 这座桥搭好之后，桥对面该放什么数据、怎么查"；I3 反过来，回答"数据库自己怎么调用模型，以及这件事的边界在哪"。

## D2：数据进库之前，先过切分这一关

D2 开场就点破了一个容易被忽略的问题：桥搭好了，桥对面放什么？很多开发者的第一反应是"上向量数据库"，但在这之前还有一个更基础的问题——原始文档怎么变成可检索的数据。

答案是切分和向量化。整篇文档直接向量化有两个毛病：一个向量代表不了文档里的所有话题，语义被稀释；检索命中后把几千字塞给模型，浪费 Token 还干扰注意力。切分的几条原则里，我觉得最容易被轻视的是**保留元数据**——来源文档、章节、更新时间。这些信息看起来和语义检索无关，但它们就是后面结构化过滤的原材料。我在 Task02 就吃过这个亏：命中的文档可能属于别的租户、还没发布，相关不等于可见，而过滤的前提是入库时就把这些字段存好。

三种进阶分块策略，我读下来的感受是它们不是并列的三选项，而是针对三种不同病症的药：

- **语义分块**治"按字符切不管语义边界"——错误码说明被切成两半，检索只命中半句话。用相邻句相似度的跌幅找话题跳变，且阈值用 percentile 而不是写死的常数，让切分线跟着当前文档自己的分布走。代价是每个句子都要调一次 Embedding API，成本实打实地高。
- **动态 overlap** 治"边界风险不均匀"——标题、段落边界的语义密度和段落中间完全不同，只在边界附近加大重叠。这是三种策略里性价比最高的升级，几乎零额外成本。
- **父子 chunk** 治的是另一个矛盾：小块检索精准但上下文不够，大块上下文完整但语义被稀释。它的解法是把**索引粒度和返回粒度解耦**——子块建向量索引，命中后按 parent_id 返回父块给模型。"搜到什么"和"给 LLM 什么"分开，这个思路比策略本身更值得记住。

Embedding 选型那节，我提炼出的主线是：MTEB 排行榜只负责缩小候选范围，真正作数的是拿 20–50 条真实业务查询跑 Recall@K——排行榜反映通用能力，业务数据反映实际效果。而工程细节里最致命的一条是**入库和查询必须用同一个模型**，两个向量空间不一致，检索结果断崖式下降，换模型就意味着全量 re-index。

## D2：向量搜索会犯蠢，混合搜索是工程现实

这一节的核心案例很简单：知识库里全是错误码文档，用户搜"E-4012 的解决方案"，纯向量搜索返回的是 E-4011、E-4013——因为在向量空间里它们语义几乎一样近，排序都带随机性。Embedding 模型训练时学到的是"语义"不是"字面"，它理解不了"差一位数字就是完全不同的错误"。

关键在于原文对这件事的定性：**这不是模型问题，是搜索策略问题**。换更强的 Embedding 模型救不了它，因为这是向量搜索这个方法论的固有边界。

所以答案只能是混合搜索：向量负责"找意思最接近的"，全文负责"找包含这个确切词的"，关系过滤负责"只在允许的范围内找"。这三种能力覆盖的是不同场景，不是"哪个更好"的选择题——任何只用其中一种的方案都有明显盲区。

"三个厨房"的类比把工程代价讲得很透：向量库、搜索引擎、关系库三套系统，三套部署、三套 API、三套数据同步，应用层写胶水代码合并结果。而其中最难的其实是一件事——一个系统按相关性分数排序，一个按 BM25 分数排序，一个按时间排序，三套排序逻辑怎么合成一个统一排名？seekdb 给出的主张是一个引擎原生支持三种检索，让向量分数和全文分数在引擎内部联合排序，而不是在应用层做事后合并。我认同这个判断的方向：事后合并永远丢信息，因为合并的时候原始排序依据已经不可比了。当然，"一个引擎搞定"省掉的是胶水代码和同步负担，索引设计、权限治理、评测这些活还是自己的——这一点 Task02 写 I1 时我就已经记下了。

## I3：AI Functions 是长得像 SQL 函数的远程网络调用

I3 把视角反过来：不只让数据库存数据、被查询，还让 SQL 直接调用模型——`AI_EMBED` 向量化、`AI_RERANK` 精排、`AI_COMPLETE` 生成，模型结果继续参与 SQL 表达式和写回。

这节我印象最深的是那个核心心智模型：`SELECT UPPER(title)` 和 `SELECT AI_COMPLETE(...)` 外观几乎一样，但执行语义完全不同。前者在数据库进程内跑，微秒级、确定性、失败只是计算错误；后者是一次**远程网络调用**——延迟以秒计、结果不确定、可能被限流超时、按 Token 计费，而且已发生的推理和费用不能随事务回滚。把 AI 函数当普通函数写，最大的风险就是忘了这五件事。四个函数里 `AI_PROMPT` 是唯一的例外，它只在本地做模板组装，不访问模型服务。

逻辑模型与端点分离的设计我觉得很务实：SQL 里只写 `doc_embedding` 这样的稳定业务名，URL、密钥、Provider 都收敛在端点配置里，换模型服务商不用改业务 SQL。但原文特意提醒了一点容易忽略的——换端点不是"无影响的运维动作"，物理模型变了，向量空间、分数分布、输出风格都可能变，应该进模型变更和回归评测流程。这和上一节"入库和查询必须同模型"是同一条原则的两种表现：**模型一换，历史数据就要重算**。

## I3：成本、事务和适用边界

成本核算的口径和我预想的不一样：不是一条 SQL 一次请求，而是**按表达式实际求值次数算**。对 500 行数据做 `AI_COMPLETE`，就是最多 500 次远程请求。所以"先过滤，再调用"不是风格建议，是费用问题——用 SQL 精确缩小集合，再让模型只看到缩小后的数据。这个逻辑和 I2 讲 Rerank 时"候选先收窄再精排"是一脉相承的：模型的调用永远应该发生在集合受控之后。

事务那节是整篇最颠覆直觉的：`UPDATE ... SET summary = AI_COMPLETE(...)` 之后 `ROLLBACK`，数据库能撤销 summary 的写入，但撤销不了已经发生的网络请求、推理和费用。外部推理根本不在数据库事务的保护范围内。给出的两阶段模式很清晰——短事务读取并固化输入，事务外调模型、校验结果，再短事务写回。这其实就是把"模型调用"当成一个和数据库平级的外部系统来对待，而不是数据库的一个函数。

适用边界的判断标准我抄在这里，它同时回答了"什么时候不该用 SQL × AI"：

> 越靠近数据、集合越小、输入输出越结构化、失败边界越清楚，越适合进入 SQL。

反过来，多轮 Tool Calling、流式输出、需要负载均衡熔断的场景，就该留在应用层。AI Functions 的价值是缩短"数据选择—模型调用—结果处理"的距离，**不是取消应用层**。数据库侧管数据选择、权限约束、靠近数据的模型调用和审计；应用侧管交互、编排、流式和体验。这个分工表比我预想的"全塞进数据库"或"全放应用层"都要清醒。
