本次 task 的这三篇其实是 task1 的一个延伸：P1 什么情况下需要 agent、如何评估；D1 chatbot 和 agent 的最本质的差别 Tool use，也是 agent 获取数据的关键；I1 讲数据如何存放。其实合起来还是那一句话——Agent 的天花板在数据，而不在模型。

## P1：值不值得做，先问数据在哪

文章开头那个"论坛小助手"的弯路让我印象很深：用户抱怨答非所问，第一反应是换更强的模型，换成 GPT-4o 之后满意度几乎没发生改变；最后翻反馈看对话才发现，知识库里根本没有答案，或者内容是几个月前的。作者说自己的错误不是技术选型，而是问题诊断。这句话其实前面的 F2 中也提到了——**先判断问题在哪一层，再决定往哪一层投资源**。

哪些场景其实不需要 Agent，文章列了三类：固定答案的 FAQ、结构化数据查询、对准确性零容忍的计算。我的概括是，它们的意图都很精确、答案也很确定，用不上 Agent 擅长的语义理解和组合推理。硬塞一个 Agent 进去，不是大材小用，而是多了一堆出错环节。

三维度评估是这节的核心：数据可得性、任务可定义性、流程编排选择。这里我一开始理解错了一处。我把"任务可定义性"读成了"模型能不能理解这个任务"，陪练时被纠正：它问的其实是**业务方能不能说清什么叫做对了**。因为大模型的输出是概率生成，还有幻觉，传统软件那套"预期输出对实际输出"的测试方法直接失效，所以立项时必须先把两件事说明白：输出形式的边界在哪，事实正确性怎么验证。模型能力差和任务难定义是两件正交的事，不能混。

我最近在想的一个企业知识助手场景也类似：文档散在员工本地、GitHub 仓库和飞书，还有一些 SOP 只存在几个老员工的脑子里。读完这篇，我最大的感受不是"该怎么设计 RAG"，而是**把这些数据找齐、整理干净，本身就比设计 RAG 更难**。数据不存在，后面全是空中楼阁。文章那句话我记住了：90% 的 AI 功能失败不是模型不行，而是立项时没人问"数据在哪"。换模型也救不了——能力上限是乘法，数据这一项接近零，乘出来还是零。

## D1：Tool Use 是取数的协议，不是模型的能力

这一节我跑完了全部示例，但一开始并不知道自己在看什么。到了陪练里才对上号：`d1_1` 是基础调用，`d1_2` 是多轮消息，`d1_3` 是流式输出，`d1_4` 用手写的循环演示 Tool Use，`d1_5` 接上真实的向量库，`d1_6` 用 `create_agent` 把手写循环收掉。

Messages 那一节让我确认了一件事：模型没有记忆。所谓多轮对话，就是每次把历史消息重新发一遍；这份"记忆"只活在这次运行的内存里，脚本一结束就没了。Streaming 则是体感问题：首 Token 出现得快，用户就觉得它在思考；等全部生成完再显示，就像系统卡住了。

Tool Use 是我觉得这次最重要的部分。我原来的理解是"模型调用了工具"，更准确的说法是：模型只是输出一个调用声明，真正执行工具的是我写的代码，执行完再由代码把结果送回模型。所以 Tool Use 不是一个功能，而是模型和本地代码之间的一套协议——我定义工具长什么样，模型判断什么时候该用它。

这个理解在跑 `d1_5` 时得到了验证。那个知识库只有 4 条文档，演示问题却问"seekdb 中提到了 RAG、Agent Memory 和 MCP 相关知识吗"。模型反复检索了 6 次都没命中，最后调了"列出全部文档"的工具，发现确实没有，就老实回答没有。我一开始以为调这个工具是幻觉，后来才想明白：幻觉是编造答案，这是换了种方法求证，是 Agent 应有的行为。它也说明工具能取数，但不能造数。

顺带纠正一个我之前的错觉：`create_agent` 省掉的是循环控制——绑定工具、检查调用、执行、回填、再调用。但 tools 列表、system prompt，以及工具背后真正的数据，还是得我自己给。管道可以封装，水得自己接。

## I1：数据要有落点

为什么 AI 时代还需要数据库？我的理解是：LLM 的每次调用都是无状态的，而业务状态、权限、回答依据来自哪份文档、记忆由谁写入能不能撤销，这些都得有地方存。而且这些数据被卷进了检索、推理、工具调用和状态修正的每一个环节，不再只是后台存最终结果。

"AI 原生数据库"我起初以为是个产品标签，读完更愿意这样理解：当数据规模不大，又不想同时维护关系库、向量库和搜索引擎三套系统时，用一套东西同时管关系、向量、文本和 JSON 数据，做混合检索，减少跨系统同步和运维的负担。但统一不等于省事——索引设计、模型调用成本、权限治理、评测，仍然是自己的活。

混合检索这一节我笔记原来是空的，这次补上了。链路是：问题转向量做语义召回，同时保留原文做关键词召回，两边各取 Top-K，再融合排名，必要时对有限的候选做重排。向量回答的是"像不像"，SQL 条件回答的是"能不能看、是否有效"。融合用 RRF 而不是直接相加，是因为向量距离和 BM25 分数的量纲不同，硬加会让其中一边的权重失真，按名次融合更稳。

这里我连着错了两次：讲链路时漏了业务过滤，做选型题时又把"相关性"和"可见性"混了。后来我才真正想清楚——命中的文档可能属于别的租户、还没发布、或者当前用户根本没有权限。相关不等于可见，过滤必须在召回时就生效。

Fork / Diff / Merge 我的第一反应是"像 Git"。方向没错，但细节也踩了坑：我把沙箱造成的一致性窗口和异步索引混成一件事。沙箱隔离的是试写，主表并没有被改动，用户看到的是旧的但正确的数据，只是改动还没采纳；"写完立刻搜不到"才是异步索引的窗口。Merge 也不是保证并发一致性——那是事务的事，Merge 是采纳决策。

用 Trae 做数据底座评审时，我承认自己对它具体怎么存数据并不清楚。这算是我留给后面的问题。

## 本次 Task 的感受

这次最真实的感受来自 D1：代码全部跑通，但我不知道要看什么。跑通不等于理解，输出正确也不等于知道为什么。真正对上，是在被问"这个循环什么时候停"的时候——我答了"超过轮次就停"，其实到上限是报错退出，正常停止只有一种：模型不再请求工具、直接给出最终回答。

三篇连着读下来，我反而更确信开头那句话。P1 说数据决定值不值得做，D1 说工具只是取数的协议，I1 说数据得有个能检索、能约束、能恢复的落点。模型一直在被讨论，但真正决定成败的，始终是数据在不在、对不对、拿不拿得到。
