## P1：先问值不值得做

这一节最让我记住的是开场那句话：先判断问题在哪一层，再决定在哪一层投入资源。课程里论坛小助手的例子很典型——答非所问不是模型理解错了，而是知识库里根本没有对应内容，或者内容停留在几个月前。把当时最强的模型换上去，满意度几乎没有变化。问题不在模型层，在数据层。

顺着这个思路，课程先唱了反调：哪些场景其实不需要 Agent。我记了三类：

- 有固定答案的问答流程，比如退款政策、报销流程；
- 结构化数据的查询，比如上月 GMV、本区域签约客户数；
- 对准确性零容忍的计算，比如含税金额、月还款额。

它们的共同点是意图精确、答案固定、不需要组合推理。硬塞一个 Agent 进去，不是大材小用，而是多引入了一层不确定性——FAQ 页面不会幻觉，Agent 会。

然后是三维度可行性评估，我按自己的话整理：

**数据可得性**：Agent 要用的数据是否真的存在。拆开是三件事——内容能不能覆盖问题、数据质量是否还准确、Agent 有没有途径拿到（有没有 API、要不要特殊权限）。课程把它排在第一位，也给了最朴素的验证方法：列 10 个典型问题，去找答案数据在哪，找不到 6 个以上就别急着上 Agent。

**任务可定义性**：怎么算做对了。LLM 的输出是概率采样，同一个事实可以有多种表述，所以要先划清输出形式的边界，再想清楚事实正确性怎么验证。有事实锚点的任务（物流状态、用户反馈原文）可以用事实当底线；没有事实锚点的任务，就得建立主观评估机制，比如多人打分或 A/B 测试。这一点我很有共鸣：没有评估标准，上线之后就会陷入"用户说不好用，但我不知道哪里不好用"。

**流程编排的选择**：Agent 还是 Workflow。我的判断依据是三条——路径能不能预先写清、错误代价高不高、数据源是不是分散。这里我自己补了一层理解：数据源分散时，Agent 得用更多上下文在不同数据源之间搜寻，代价更高；Workflow 可以把数据需求拆到每一步，各步分别调 API，只有需要语义理解的环节才交给模型。所以课程说"先 Workflow，再 Agent"，本质是先用手上确定的东西换一个可控的验证。

Checklist 我按 3+1 记：场景匹配度、数据可得性、任务可定义性、流程编排选择。前三项判断"该不该做"，最后一项决定"怎么做"。

Agent 的三个甜区则是反面：语义理解（用户说不清楚要什么）、工具调用（能做事而不只是说话）、持续交互（多轮里逐步逼近真实需求）。命中两三个，才值得考虑。

## D1：Tool Use 才是聊天机器人和 Agent 的分界线

D1 从最基础的地方讲起，但纠正了我一个想当然的理解。

**Messages**：多轮对话的本质不是模型记住了什么，而是每一轮都把更新后的 messages 数组整体发给模型，让它基于整段对话历史做一次新的回答。模型本身没有记忆，所谓对话历史全靠开发时自己维护这个数组。这一节把 F1 讲的上下文窗口落到了工程层面：能传多少历史，取决于窗口能装多少 Token。

**Streaming**：首 Token 延迟比总生成时间更重要。用户能接受边生成边看，不能接受等十几秒然后一次性弹出——这更多是交互和显示层面的要求，但确实是体验的关键。

**Tool Use**：这是这一节最重要的部分，也是我原来理解错的地方。我以为"模型调用了工具"，实际上模型做不了这些事——它只是在输出里声明：我需要调用某个工具、参数是什么。真正执行的是我写的代码：代码读到输出里的 tool call，去执行对应的函数或 API，再把结果作为一条新消息传回去，模型基于结果继续推理。

想通这一点，很多东西就顺了：模型能调用什么工具，由我定义；工具怎么执行，由我控制；结果怎么处理，也由我决定。Tool Use 不是模型的内置能力，而是模型和代码之间的一份协作协议。也正因为如此，它才是聊天机器人和 Agent 的分界线——没有它，模型只能基于知道的东西回答；有了它，模型才能决定去查库、调接口、做事。

## I1：AI 产品是无状态的，数据得自己存

I1 回答的是一个看起来反直觉的问题：大模型这么强，为什么 AI 应用还离不开数据库。

我的理解是：无论是聊天工具、Agent，还是最近很火的各类 AI 产品，对 LLM 的调用本质上都是单次、无状态的——模型只是根据你给它的信息生成一次结果，调用结束，它那边什么都不剩。既然产品本身没有状态，状态就只能由我们自己存。

和传统后端相比，我不觉得这是"多存一点东西"的差别。传统后端更多是在流程末尾保存最终结果；AI 产品则把数据的存储和使用融进了使用的每一个阶段——检索、推理、调用工具、修正状态，每一步都在读数据、写数据。课程后面讲的混合检索、数据库内 AI、Fork/Diff/Merge，其实都是围绕这件事展开的。
