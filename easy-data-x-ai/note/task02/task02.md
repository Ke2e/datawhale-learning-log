### P1：AI Agent 场景识别

> 道篇第一节：判断“这个需求值不值得用 Agent 做”。原文结构：开场“论坛小助手”弯路案例 → 哪些场景不需要 Agent → 三维度可行性评估（数据可得性 / 任务可定义性 / 流程编排选择）→ 场景评估 Checklist → Agent 的三个甜区 → 数据隐私与本地 Agent。

#### 哪些场景其实不需要 Agent（不需要 ai 的介入）

- 有固定答案的问答流程
- 结构化数据的查询
- 对精确度 0 容忍的计算

#### 三维度可行性评估（数据可得性、任务可定义性、流程编排的选择）

- agent 能否获得其需要的数据
  - 内容是否全面可以覆盖问题
  - 数据内容质量是否合规
  - agent 是否可以获取这些数据
- agent 需要解决的问题是否有确定的标准来评判它是否正确
  - 输出形式的边界在哪（结构化输出？）：怎么样的答案算对
  - 实时结果的准确性是否有保障
- agent vs workflow
  - agent：复杂问题处理、解决问题的流程由 agent 全权决定、问题解决路径不确定
  - workflow：问题处理路径节点规定、要求严格、容错率低（也就是错误代价高）
  - 如何决策 agent vs workflow
    - agent 能否获取到全部的所需的数据；Workflow 可以分步骤执行他可以在不同步骤调用 api 去获取数据（数据源是否分散，agent对于数据源分散的情况需要用更多的上下文（资源）在不同数据源中去搜寻，更贵）
    - 问题处理路径节点是否确定（也就是是否有确定的问题解决流程）
    - 错误导致的代价高吗

#### 场景评估 Checklist（3+1）

- 场景匹配度
- 数据可得性
- 任务可定义性
- 流程编排选择

#### Agent 的三个甜区

- 语义分析
  - 用户对于问题的表达不清晰，需要 agent 进行分析，或者多轮交互获取更多信息来进行问题的完善，agent也可以进行问题的拆解
- Tool Use
  - agent 能够调用外部工具
- 持续交互能力
  - 通过持续交互增添关于问题的相关信息

### D1：大模型 API 基础

> 术篇第一节：从“用 ChatGPT”到“用 API 构建 AI 应用”。原文结构：Messages 与多轮对话 → Streaming → Tool Use（重点）→ 从手动编排到 create\_agent。

#### Messages：对话的本质是一个列表

- 多轮会话本质是每一轮对话都将更新后的 messages 数组通过调用 api 发给大模型，让他更加这整个对话历史来进行一次新回答罢了
- 所以开发时，需要自己注意维护这个数组，这也就是上下文窗口的关键

#### Streaming：首 Token 延迟

- 显示要求（类似前端的存在价值），是交互的关键

#### Tool Use：让模型从“只能说”变成“能做事”

- agent 与 genAI（chatbot）的关键差别
- 实际上不是 llm 调用了工具，是你写的代码调用了那些工具的 api，是代码检测到 llm 的输出的文本中可能带上了某个属性，这意味着需要调用工具，所以对应的代码执行
- 感觉Tool use 其实也是一种协议，它是大模型和你实际在本地运行的工具代码之间的一种协议。

  包括现在关于大模型的训练，它也会把 Tool use 的框架结构化下来，这样可能更便于他们训练，提高训练效率。

  所以 Tool use 并不是一个功能，而是一个协议：是你本地规定好我的 Tool 应该有哪些字段，然后大模型也能更好地读取。它知道一个 Tool 要读取哪些字段，也知道要根据什么决定这个 Tool 什么时候运行。

### I1：AI 原生数据库基础

> 产业篇第一节：回答“AI 应用为什么仍然需要数据库”与“什么样的数据底座更适合 Agent”。原文结构：为什么需要数据库 → 六个观察维度 → 统一数据库六层架构 → LSM-Tree → 一份事实多种表达 → 混合检索 → 数据库内 AI → Fork/Diff/Merge → 嵌入式与服务器模式 → 选型 → 企业知识助手案例 → 常见误区。

#### AI 时代为什么还需要数据库

- 因为 ai 产品（chatbot、agent、最近很火的 PA ）本质对于 LLM 的使用都是单次的无状态调用，llm 就是根据信息回答结果而已。既然 ai 产品本身是无状态的，那就需要我们手动进行数据的存储。并且相较于传统后端，ai 产品将数据的存储、使用等融进了 ai 产品使用的每个阶段

#### AI 原生数据库的六个维度

- AI 原生数据库的要求，或者说它面向的产品需求是：当在一些数据规模没有那么大，后端实际延迟、写入频率、一致性、团队经验、成本和运维边界等场景压力没有那么大的时候，再去做传统的关系型数据库加向量型数据库，再加上搜索引擎的组合，就会特别冗余。

  当然，这三个组合带来的产品后端数据库相关能力肯定是非常巨大的，但也会给这个产品带来极大的负担。所以 AI 原生数据库就是将这三个部分，也就是数据的向量化存储或者关系性存储，以及数据库当中的数据检索机制，包括向量检索、关键字检索、混合检索，通通整合进一个原生数据库，来减轻小型、中小型产品对数据库的负担，让它们不用去安装多个数据库，并且可能还要安装专门的搜索引擎，来实现它需要的检索相关功能。
- 六个维度

  - 能否同时存储关系型数据+向量型数据+文本型数据（通常是存储在向量数据库中）
  - 能否进行混合检索（关键词检索+向量检索+融合过滤机制）
  - ACID 事务与恢复
  - 模型调用（问题的检索需要几轮，是否当前获取的数据已经足够回答问题）
    - 数据的嵌入、重排
    - 以及合适位置的模型调用
  - Agent 工作流
  - 多端适配

####  这个数据库的关键意义

- **同一份事实数据**可以被精确查询、语义检索和关键词检索；
- **同一个事务边界**可以同时约束业务字段和 AI 相关字段；
- **同一条执行链路**可以先缩小数据范围，再调用昂贵的外部模型。

#### SQL 的重要性

- 结构化的数据，使用 sql 进行约束与检索会方便很多

#### 混合检索：向量 + 全文 + 标量过滤 + 融合 + 重排

#### 数据库内 AI 与正确的调用顺序

- AI 的调用相比数据库中的检索、通过代码实现的筛选剔除，都要更贵，所以先对数据进行一些筛选，再使用 ai 进行重排或生产会更加合适

#### Fork / Diff / Merge

- 由于 agent 能操作 ai 原生数据库，能对数据进行一些修改，所以需要更加完整的对于数据的版本保障系统（类似 git？）

思考题

1. 因为向量相关，或者说回答的这个与问用户的问题之间，它的向量相关性很高，并不代表这就是用户需要的问题的答案。例如像高血糖与低血糖相关的，那由于它们都有血糖这个部分的这个语义，所以它们在向量的检索程度上相关性又非常高，但是它们两个的具体的一些，呃，就是关于他们两个具体的一些问题的答案，可能可以说是完全相反的，所以向量相关性并不能作为唯一的呃用户答案的答用户问题的答案的这个评判标准。
2. 这个问题，或者说这个这两种情况它的，或者说这两种索引同步方式的所适配的情境是不一样的，前者是为了保证最终一致性以及在使用过程中的低占用也就是在尽可能少的，或者说尽可能少使用资源的情况下，保证数据的一致性。它就是逐步地对数据进行写入，然后最后在一个时间内保持它的就是最终一致性。那，毫无疑问，它肯定是有一个一致性窗口，那在窗口当中，它的数据肯定和实际数据是不一致的。但是与此同时，它可以说是减少了我们数据写入的这么一个同一时间的一个流量。那后者就是实时的对数据的更改进行写入，所以当我们的写入请求十分多的时候，它的 QPS 已经超过了我们，呃，系统的这个能够承载的程度的时候，我们可能就需要使用异步向量检索来进行数据的写入。
3. 因为 RRF 避免了向量分数，或者说向量距离与 BM25 分数之间的权重分配。它是直接按照向量在向量中排序、BM25 在 BM25 中排序，然后将两个部分的排名情况作为评判标准，而不是把向量距离以及 BM25 分数直接相加，这种非常简易的方式。所以它更能表明各自在各自情况下的大致排名，使用直接相加可能会导致两者有一边的基数过大导致另外一边对于结果的影响过小
4. fork 是保障了原数据的安全，也就是不直接修改主数据库，那我们的主数据库就会安全，他是在 fork 出来的数据库上进行修改嘛。diff则是使得数据的变更更加的清晰可记录，否则你要做快照的话，就是要将每一次的数据库的情况都直接快照下来，那它对于存储的要求是非常高。Merge 就是保证多数据修改，或者说并发时进行数据修改的一个场景。它能够将同时进行数据修改时的 diff 进行 merge 合并。这样的话，就可以说是很好地实现了并发数据修改场景下这个问题的解决吧。
5. 不知道，还没有具体使用过

#### Q1 · 事实层：三个维度是从哪推出来的

- 日期：2026-11-23。
- 依据：[P1 第二部分：三维度可行性评估](<../../upstream/docs/pm/P1 课程稿：AI Agent 场景识别.md#第二部分三维度可行性评估>)，能力上限公式“数据质量 × 模型能力 + 流程编排”。

#### Q1 · 事实层：一条混合检索链路与 RRF

- 日期：2026-11-23。
- 依据：[I1 第 6 节混合检索](<../../upstream/docs/industry/I1 课程稿：AI 原生数据库基础.md#6-混合检索从相似走向可用>)（RRF 公式、同步/异步索引）。
- 问题：① 一条完整的混合检索链路依次包含哪几步？② 为什么不能把向量距离与 BM25 分数直接相加，而要用 RRF？③ 若要求“写入后立刻能被检索到”，该选同步还是异步索引？代价是什么？
- Asize 原始回答（2026-11-23）：① 分两部分：向量检索（问题做 Embedding 后检索，取 Top-K，按向量距离）与关键词检索（原文文本做关键词匹配，取 Top-K，用 BM25 打分）；两者取到后通过 RRF 重排筛选，再把结果交给 LLM 生成答案。② 两者单位不同、基数不同，直接相加会导致权重分配不合理；RRF 用各自通道内的位次组合，更合理。③ 用同步索引，代价是并发写入能力受限、对系统资源占用更高。
- 助手反馈（2026-11-23，单独标注）：① 部分过线，漏三步：a) 召回前或召回过程中的业务过滤（租户、权限、时间、状态、JSON 属性）——它决定“能不能看”，而向量只回答“像不像”；b) RRF 是“融合排名”，重排（rerank）是另一件事，对融合后的有限候选再用模型打分，你把两者合成了一步；c) 返回结果应带业务字段、分数与证据来源，便于引用与追溯。② 正确，抓住“量纲不可比”；可补：RRF 中 k 用于平滑头部排名的波动，且不要求各召回器的原始分数可比。③ 正确；可补：同步索引把维护成本压在事务关键路径上，异步则是先提交基表、再追平索引，存在最终一致窗口。判定：② ③ 过线，① 待复验（业务过滤见 Q2③）。
- 提示情况：未给解法提示；反馈含原文对照。
- 掌握结论：② ③ 过线，① 部分过线。

#### Q2 · 决策层：统一数据库，还是组合式架构？

- 日期：2026-11-23。
- 依据：[I1 第 10 节选型](<../../upstream/docs/industry/I1 课程稿：AI 原生数据库基础.md#10-选型统一数据库还是组合式架构>)与常见误区。
- 问题：① 场景 A（50 人团队的企业知识助手，百万级文档，检索必须带部门与权限过滤，后端仅 2 人）与场景 B（公开电商搜索，日 PV 上千万，要求极低尾延迟与专门的中文分词调优，已有搜索团队）各选哪种架构，依据哪些判断项？② 场景 A 用统一数据库后，还有哪些事必须自己做？③ “向量召回结果很相关”为什么仍不代表可以展示给当前用户？
- Asize 原始回答（2026-11-23）：① A 统一数据库，B 组合式；依据是对应各自的使用频率、维护成本、业务过滤、检索负载上限。② 还需要做数据整理与入库、数据维护。③ 向量相关性只保证语义相近，不能保证召回的就是用户要的答案；如高血糖与低血糖语义相关性很高，但答案可能大相径庭，所以还要靠关键词检索进一步匹配。
- 助手反馈（2026-11-23，单独标注）：① 判断正确，可点名为原文判断项：A 命中“中小规模、数据类型多、强调开发与运维简化 + 业务过滤与语义检索强耦合”；B 命中“单一检索负载达极大规模、需要专用能力”。② 不全：统一数据库省掉的是系统边界，不会消除索引设计、模型成本、权限治理与评测；你只说了数据整理与维护。③ 偏题：你答的是“相关性 ≠ 答案正确”（高血糖/低血糖例子准确，属事实正确性问题）；本题问的是“相关性 ≠ 可见性”——命中的文档可能属于其他租户、未发布、或当前用户无权限。这两类失败模式不同，业务过滤必须在召回时生效。判定：① 过线，② 部分过线，③ 偏题；Q1① 的业务过滤点复验未通过。
- 提示情况：未给解法提示；③ 反馈含原文对照纠偏。
- 掌握结论：① 过线，② 部分，③ 待再验证。

#### Q3 · 反事实层：Agent 批量改写记忆表，直接写还是走沙箱？

- 日期：2026-11-23。
- 依据：[I1 第 8 节 Fork / Diff / Merge](<../../upstream/docs/industry/I1 课程稿：AI 原生数据库基础.md#8-fork--diff--merge给-agent-一个可写沙箱>)、第 3.2 节事务，及原文思考题 4。
- 问题：① 两种方案（直接写主表 / Fork 沙箱试写后 Diff、Merge）各自的风险是什么？② FAIL、THEIRS、OURS 三种冲突策略分别适用于什么情况？③ Fork/Diff/Merge 与数据库事务分别解决什么问题？
- Asize 原始回答（2026-11-23）：① 直接写主表可能改错数据，且错误会立刻被其他读操作看到；并发读写没有冲突验证，容易数据错乱。沙箱的问题是不实时修改，用户观察与数据库之间存在一致性窗口，窗口内看到的信息不是真实数据。② FAIL 用于默认情况或需要审查合并；THEIRS 用于 Agent 的修改已被证实；OURS 用于主数据优先。③ Fork 提供误操作的兜底；Diff 减轻多版本管理难度，比整库快照省资源；Merge 保证并行读写的一致与合理，只有符合条件的写入才能合入主库，相当于业务审查；事务保证一致性并可整体回滚。
- 助手反馈（2026-11-23，单独标注）：① 前半正确（污染主数据、并发无冲突检测）。后半不成立：沙箱隔离的是“试写”，主表未被改动，用户看到的是旧的但正确的主数据，只是“改动尚未采纳”；“一致性窗口”是异步索引的特征（写后可见性延迟），不是 Fork 的特征，两个机制不能混。② 全对。③ 方向对但 Merge 职责说串：Merge 是采纳决策（按策略把沙箱变更合入主数据、处理冲突），并发一致性属于事务/MVCC；原文明确 Fork/Diff/Merge 只解决隔离与采纳，不替代权限、审批和审计。与事务的分工：事务管一次执行内要么全成、要么全回滚；Fork 管决策前的隔离试写与受控采纳。判定：② 全对，①③ 部分过线。
- 提示情况：未给解法提示；①③ 反馈含原文对照纠偏。
- 掌握结论：② 过线，①③ 部分过线。

#### Q4 · 复验：三条召回结果，谁能给这个用户看？

- 日期：2026-11-23。
- 依据：Q1① 与 Q2③ 两次未接住的“业务过滤”；[I1 第 3.1 节 SQL 与检索条件](<../../upstream/docs/industry/I1 课程稿：AI 原生数据库基础.md#31-sql-为什么仍然重要>)；原文思考题 1。
- 问题：用户 A（tenant_id=7，普通员工）在企业知识助手里搜“报销流程”，向量召回返回三条最相似文档：doc1（tenant 7，已发布）、doc2（tenant 8，已发布）、doc3（tenant 7，状态 draft）。① 三条分别能不能给 A 看，为什么？② 应该在哪一步拦住？③ 如果只按相似度返回 Top-3 会发生什么？
- Asize 原始回答（2026-11-23）：① doc2 不可以，因为所需权限 A 没有。② 应该在查询后、召回前被筛选掉。③ 会让企业数据的机密性受挑战，很多人能看到本不该看的数据。
- 助手反馈（2026-11-23，单独标注）：① 部分：doc2 判断正确（跨租户）；doc1 可看（同租户、已发布）；doc3 不可看——同租户但状态是 draft，未发布不应对外。你只覆盖了租户权限，漏了状态维度。② 表述自相矛盾（“查询后、召回前”）：过滤条件应写进召回查询本身（SQL 的 WHERE），与向量检索在同一条语句里执行，而不是先取回再筛。③ 正确；可补：除泄密外，还会把未定稿内容当作依据，答案质量与用户信任一并受损。判定：③ 过线，① 部分，② 需精确；I1 收束，判基本达标，薄弱点记为“可见性过滤（状态维度）”。
- 提示情况：未给解法提示；①② 反馈含原文对照纠偏。
- 掌握结论：I1 基本达标（待 Asize 确认）；薄弱点：业务过滤中的状态/发布条件。
