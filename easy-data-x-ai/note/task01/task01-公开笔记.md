## F0： 为什么 OpenClaw 越来越好用

我之前接触过 OpenClaw，所以这一节读起来有一些自己的理解。首先我赞同文中的判断：Agent，甚至可以说大部分 AI 产品，都十分需要数据。现实里也是这样——面对一个任务，获取的信息越多，就越少走弯路，处理起来也更简单；对 Agent 来说更是如此。

这一节的顺序是先从 OpenClaw 讲到 Agent：先说 OpenClaw 好不好用，关键在数据；再拆它的底层设计机制——怎么收集和利用数据，从而实现所谓的自动进化；再从 OpenClaw 推到 Agent，数据的重要性也就自然成立了。我觉得它其实是在潜移默化地种下"数据"这颗种子。

课程把原因概括成一条公式：**AI 产品的能力上限 = 数据质量 × 模型能力**。在"同一个产品、底层模型不变"这个前提下，我认为这个说法是成立的：模型决定它有多聪明，数据决定它知道什么、记得什么，两者合起来才决定它在我这件事上做得怎么样。

我想在这条公式上补一层：产品自己对数据的获取、辨析、清洗（或者说是权重划分）和使用，同样构成上限。因为不同的人提供数据的能力并不好把握，有时甚至要看运气——我的表达方式刚好适合它，我用起来就更舒服。

它的核心机制也不是悄悄换了一个更强的模型，而是把我们的提问和结果反馈汇总起来，提炼、增补进 Agent 自己的数据里。陪练时，我一开始把"上一轮的教训怎么影响新会话"答成了 Agent 按需去检索文件；对照 F0 原文才发现方向反了：核心规则是框架在每次对话开始时自动全量加载进 system prompt 的，触发者是框架代码，不看这一轮问了什么。想清楚这一点，整条链上唯一变化的变量也就清楚了——模型权重、工具权限、程序代码都没变，变的是这一轮的输入。LLM 本身没有状态，"它记住了"更准确的说法是"它这一轮看到了"。

最后落到使用上：用好 Agent 的关键是提供数据，不一定需要我会编程；但提供什么数据、怎么提供，确实还需要我逐渐学习和掌握。

## F1：大模型的局限，根子都在数据

课程列了三个局限：幻觉、知识截止日期、个性化盲区。我的概括是：它会编、它只学到某个时间点、它给的是通识答案。三者看起来不同，根本原因却是一个——大模型是预训练出来的，训练数据里没有"我"的数据，也没有解决我这个具体问题所需要的数据。所以用好 AI 的关键又回到数据：提供、处理、储存。

Token 和上下文窗口这两节我原来在笔记里空着，这次补上了。Token 是模型理解和处理信息的最小单位，怎么切由厂商的词表决定，所以同一段文字在不同模型里的 Token 数可能不同；上下文窗口则是它单次能装下的信息总量。两件事连起来解释了一个现象：上下文是有限预算，往里放什么、放多少，都要付代价。F0 里核心规则每次全量加载会带来上下文过载，说的就是这个成本。

最近一次让我印象深的，是让 Trae 帮我装项目依赖，一直装不上。当时我在笔记里写了两个判断：一是安装过程的信息获取不够，二是模型对错误的处理不够好。后来我原样重跑了一遍，它又自己好了，这反而让我更说不清该归因给谁。

用 F1 的框架重看，所谓"缺的用户数据"应该是很具体的东西：操作系统与运行时版本、包管理器类型、报错输出和退出码、依赖装到了哪里、项目根目录和虚拟环境状态。这些数据都在我的机器上，预训练语料里没有，正好落在"个性化盲区"里；模型并不是不会用 pip，所以知识截止和幻觉都不是主因。

为了不再靠感觉归因，我设计了一个对照实验：同一台机器、同一个项目、同样的安装要求，一组只给要求，另一组附上环境清单和依赖现状，每组重复几次，看成功率的差别。方案有了，还没跑——这里先记下的是实验设计，不是结论。单次"重跑就好了"也提醒我，一次失败不足以归因。

## F2：四个新概念，位置不同，处理的是同一种东西

Agent 的能力公式是 **模型能力 × 数据质量 + 流程编排**。课程反复强调：Agent 不是更强的模型，而是靠 ReAct 循环真正能拿到外部数据、并采取行动的工具，核心组件是 LLM、Memory、Tool use 和 Planning。

我按课程推过一遍 ReAct：任务是查到磁盘上最大的文件夹再删掉。第一轮推理出要用工具查大小，执行后拿到结果；第二轮推理怎么删，执行删除；第三轮根据观察判断是否成功，成功就直接回复。Observation 是工具返回的结果，会作为新消息回到上下文——框架把累积后的整段上下文再送进同一个模型。所以"模型没变却能干成"，是因为它被调用了多次：每次输出改变了世界，世界的反馈又变成下一次的输入。

Workflow 和 ReAct 不是替代关系。我的判断标准是路径能不能预先写清楚：每月经营周报，数据源和格式都固定，出错还要直接发给管理层，适合 Workflow；线上服务突然挂了，成因未知，要查日志、看监控、回滚、改配置，路径列不全，只能让 Agent 自主决策，但最好留人工在关键动作前检查。

至于 RAG、MCP、Skill、Memory，我最后把它们归到一句话：都是在不同位置、不同时间、以不同方式处理数据。RAG 是把 Agent 不知道的数据注入上下文，瓶颈在知识库质量、切分策略、检索策略和 Embedding 模型；Agentic RAG 和 Native RAG 的差别，是"要不要查、怎么查、查几轮"由谁决定。MCP 是工具接入的标准化协议，像 HTTP 一样统一接口。Skill 是把经验结构化成 AI 能复用的 SOP。Memory 分语义、情景、工作记忆，效果取决于提炼质量、召回策略和遗忘机制。

这个归纳也让我有了一个自己的小框架：以后遇到新的 Agent 概念，先问它在哪个场景、借由数据解决什么问题。用它看 A2A，它解决的是不同公司、不同框架的 Agent 之间互相发现、通信和委派的问题，位置在协议层——标准化的是 Agent 与 Agent 之间的通信，而不是 Agent 与工具的接入。

F2 的课后行动是给自己在用的 AI 工具画能力地图，我试着画了 Trae：

- 外部知识：能查，但我判断是 Web 搜索、工具调用，不是知识库 RAG；
- 记忆：有，存在本地文件，AGENTS.md 也可以手动写进去让它读；
- Skill：有，但我确实不清楚它是怎么被发现和调用的，只知道它存在本地文件夹里，可以删除或禁用；
- MCP：有，这一点是明确的。

这张图里空着的那块，恰好是我下一步想弄清楚的：一个 Skill 从本地文件到被 Agent 真正用上，中间发生了什么。

## 本次 Task 的感受

这次 Task 走下来，我最直接的感受是：Agent 的核心是数据，很多看起来不相关的概念也都是与数据相关的。想清楚这一点之后，RAG、MCP、Skill、Memory 这几个名词在我这里不再是并列的清单，而是同一种东西在不同位置、以不同方式的处理。
