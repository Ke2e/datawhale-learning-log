### F0：课前闲聊 —— OpenClaw 为什么越用越好用？

#### 为什么有些人觉得 openclaw 越用越趁手呢？

老师的理解是，由于 openclaw 对我们的信息或者说是数据的理解和获取更多（在其他条件不变、相同的情况下，例如底层模型等），他就更加知道如何按照我们喜欢的方式去运行和实现我们所需要他完成的任务了。也就是 **AI 产品的能力上限 = 数据质量 \* 模型能力 。** 确实，如果聚焦于同一个产品确实是这样的，底层的模型决定了这个产品的智能，数据提供给产品知识或者说记忆，这两者加在一起，那么这个产品对于该数据相关的任务的处理是会更好的。但是在这个基础上，或者说对于 ai 产品本身而言，其实产品本身对于数据的获取、数据的辨析、数据的清洗（或者说权重划分）、数据的使用也是这个 ai 产品的能力使用的上线，因为对于不同的人，他们提供数据的能力或者说提供给该 ai 产品擅长处理的数据这个能力是不好把握的，这甚至可能不算一种能力，因为有时候就是看运气的，刚好你的表达方式适合，可能这个产品就更加适合你，你使用和处理起来就更舒服。所以对于 ai 产品本身的对于数据和模型的使用也是 ai 产品提升的一个方面吧。

#### OpenClaw 的核心机制

OpenClaw 的核心机制其实就是对于数据的更新，它会根据我们的问题，以及对该问题 Agent 结果的反馈进行汇总，然后以此修改，或者说提炼、增加 Agent 当中的数据，以此来实现所谓的自主进化。

#### Agent 的使用

作者其实是借由 OpenClaw 这个 Agent 向我们展示：使用，或者说让 Agent 切实、更好地解决我们现实中的问题，让 Agent 融入我们的生活，并不需要我们学会编程。只需要我们会提供数据，能够合理、恰当地提供给 Agent，并且最好能够教他如何使用数据。这样的话，其实我们就可以合理地使用好 Agent，并且能够让它为我们的工作提效。

### F1：大模型的本质与边界

####  大模型的 3 个局限及其根本原因

1. 幻觉：大模型回答的问题可能是错误的。
2. 知识截止日期：大模型能够准确回答的切实问题，是有一个明确截止日期的。
3. 个性化盲区：大模型回答的答案通常是更加通识、更加普遍的答案，它很少会根据你所处的，或者说用户所处的具体情况，做一些个性化的改进

根本原因：大模型是预训练的模型，他训练使用的数据没有用户的数据，或者说没有解决这个用户问题所需要的数据。

所以这里就提到了，其实 AI 产品的上限，或者说用好 AI 产品的关键，在于数据：数据的提供、数据的处理、数据的储存。

####  上下文窗口：大模型单次处理信息的最大总量

### F2：AI Agent 全景图

Agent 的时代，**AI Agent 的能力上限 = 模型能力 × 数据质量 + 流程编排**

Agent 不是更强的模型，而是通过 ReAct 循环，能够切实获取物理世界中其他数据，并进行行动的完整工具。

Agent 的核心四个组件是 LLM、Memory、Tool use 和 Planning。

<br />

Agent 目前使用的主要核心架构为 ReAct 架构 Reasoing -> Acting -> Observation，对于 ai 产品还有就是预定编排过的工作流架构（Workflow），这两者并不是升级替代关系，两者都有自己的使用场景。agent 适合用于需要大模型对问题进行分析然后设定决策方案的场景（不是简单的根据现实问题进行路由之后，直接去进行对应操作的决策。这本质上还是预定的工作流，只不过对于一些问题，它有不同情况的节点设置。agent 就是需要模型自主对于问题去决策方案，生成方案，执行方案）。Workflow 就是对于该工作的一整套路径，有清晰的节点划分和使用方式。大模型在 Workflow 当中，只是作为节点内部的对于问题的一些处理方式，或者说是在面对一些情况时，由大模型来辅助问题路由。所以，Workflow 适用于高风险、切实性和具体性的工作流程，agent 就是适用于风险性没那么高，问题比较复杂，需要 Agent 自主完成的工作。

<br />

- RAG：让 agent 能够获取到外部资料，也就是知识数据的检索
  - Native RAG：
    - 固定流程
    - 单次检索
    - 无法处理复杂查询、无法自适应调整策略
  - Agentic RAG：
    - Agent 决策是否需要查、怎么查、查几轮
    - 支持多轮检索，多源交叉验证、策略调整
    - 从每次都要查询，到自主决策是否需要查询。
  - RAG 的本质，就是将一些 Agent 不知道的数据与信息，通过一些方式注入到 Agent 的上下文中，让它获取到；之后，让它有了更多数据后，去更好地处理问题。所以这里就引出了 RAG 真正的核心的瓶颈上限，就是关于这些数据，首先这些数据质量是否合格？如何让 Agent 的检索的时候能够尽可能的获取到与用户问题相对应的、合适的数据？以及如何尽可能地在保证 Agent 的智能的情况下，将这些数据注入给 Agent？也就是
    - 知识库的**数据质量**（文档完整性、更新频率）
    - **切分策略**（Chunk Size、重叠度）
    - **检索策略**（纯向量 vs 混合检索）
    - **Embedding 模型**选择
- MCP：标准化工具接入，是 Tool 的远程适配协议
  - 目的是为了解决多个不同 Agent 框架对于多个工具适配情况的一个接口协议整合，或者说一个规定，类似于 HTTP。

    目的其实就是为了让我们不同的 Agent 对于不同工具，它们之间的接口方式都是相同的，那也就使得我们可以自由地切换 Agent 和工具，并且它们之间没有结合的阻碍。MCP 统一了 AI 工具的接入协议
  - **Tool Calling**：工具调用（执行操作）
  - **Resource Exposure**：资源暴露（读取数据）
  - **Prompt Templates**：提示模板（预设交互）
  - MCP 的本质是为了数据接入的标准化
- SKILL：AI版的 SOP，本质也就是经验数据的结构化，让 ai 能够迁移使用这些之前的经验数据
  - **组成要素：**
    - 操作流程（Step-by-step 指令）
    - 领域规则（约束条件、质量标准）
    - 成功案例（历史优秀输出）
    - 术语表（领域特定词汇）
  - Skill 的效果取决于：
    - 技能**结构化程度**（是否清晰可执行）
    - **发现能力**（如何在技能库中检索匹配的 Skill）
    - **复用性**（跨场景、跨用户的适用性）
- Memory：个性化数据的积累与召回
  - Agent 记忆分为三种：

    **1. 语义记忆（Semantic Memory）**
    - 记住事实与偏好
    - 示例：“用户是 Python 开发者”、“用户偏好简洁回答”
    **2. 情景记忆（Episodic Memory）**
    - 记住过往经验
    - 示例：“上次用 Docker 方案解决了部署问题”
    **3. 工作记忆（Working Memory）/ 程序性记忆（Procedural Memory）**
    - 记住行为规则
    - 示例：“遇到代码问题先查文档再写代码”
  - Memory 的效果取决于：
    - 记忆**提炼质量**（如何从对话中抽取关键信息）
    - **召回策略**（何时调用哪些记忆）
    - **遗忘机制**（如何降权过时信息）

所以综上所述，上面提到的这些可能比较新兴的概念，其实对于 Agent 来说，都是对数据的存储与检索（处理）罢了，只不过他们可能是在不同位置、不同时间、以不同方式对数据进行处理。未来即使出现新的 Agent 相关概念，它也大概率是与数据相关的。到时候我们可以思考：它希望在哪个场景下，借由数据解决哪些问题？这样能够让我们更加清晰地明白，这个新的名词，或者说新的概念，对于 Agent 来说是什么样的地位，或者说处于架构中的什么位置。
